# nCTRL — Godot 4.7 C# / Hyundai USA

N Performance styling, pixel car art for 14 models (IONIQ 5 N by default), six paint presets including **Ecotonic Gray**, and custom paint (Settings → Appearance → Car color). This revision includes direct Hyundai USA / Bluelink HTTP connectivity, secure phone-side saved login, and biometric unlock. App logic is C# with small native OS storage bridges. No Python runtime or backend.

**Implementation status:** C# app/export plugin and Android vault Java compiled. The bundled Android AAR includes the nCTRL prompts. The iOS vault now builds with the C# NativeAOT export; Apple compilation and physical-device validation are still required. Mobile JSON serialization no longer uses reflection. See `SECURE_LOGIN.md` for mobile setup. The owner reported a live sign-in 502; this revision has not been authenticated against a real Hyundai account or tested on a physical vehicle. The working local fiveN sign-in profile was compared and adopted for token/enrollment requests; live resolution remains unverified. See `SIGN_IN_DIAGNOSIS.md`. Mobile exports have not been tested.

## Run and connect

1. Install **Godot 4.7 .NET** and the .NET 8 SDK for a desktop preview.
2. Import `project.godot`, build, and press **F5**. First build restores the Godot NuGet packages. `IoniqN.sln` retains its internal name for compatibility; the app is nCTRL.
3. The app first shows the **risk disclaimer** until the current account has accepted it (see below), then **Connect your Hyundai**, or opens the car with the saved login.
4. Enter your US Bluelink email, password and four-digit Bluelink service PIN **inside the app**. Do not put credentials into the source code or a chat message.
5. On a supported phone, leave **Save account on this phone** selected to keep the login in the phone's Keychain. Afterwards the app opens straight to the Car screen with the last saved status and, like the Hyundai app, reads Hyundai's cached status each time you open it or return to it (skipped quietly inside the read limit). No request needs Face ID; Face ID or the passcode is asked only to accept the risk disclaimer and to go past a request limit. Desktop builds remain session-only.
6. Select your enrolled vehicle once. After later unlocks/sign-ins, nCTRL matches that vehicle against fresh enrollment and loads its cached status automatically. Connecting sends no remote vehicle command.
7. A **LIVE** badge indicates the connected UI. Tapping a command sends it directly, with no confirmation dialog. One door button offers Unlock when reported locked, or Lock when reported unlocked; unknown door state disables it until status is refreshed.

**Try the demo** (on the disclaimer and sign-in screens) opens a pretend IONIQ 5 N served inside the app (`Core/DemoHyundai.cs`), for trying nCTRL without an account and for App Review. The real client code runs against it, so every screen and command works, but nothing is sent to Hyundai and nothing is saved: the header badge reads **DEMO**, the demo gets its own relaxed request limits, the disclaimer isn't needed because nothing reaches a car, and **End demo** (in Settings, where Sign out & forget would be) puts back your own preferences, saved status, request limits, ignored places and last known location. The secure login, Keychain items and saved files are never touched. The demo car sits at a public place (Central Park, New York), and its map still loads OpenStreetMap tiles; its Surround View "camera" returns the car picture. The demo carries on if the app is backgrounded. Outside the demo there is no simulated vehicle. With a saved phone account and a remembered vehicle, launching or returning to the app opens the Car screen showing the last saved status (marked with when it last updated) without Face ID or any request. The first **Update**, wake, command or location request of each foreground session asks for Face ID, which unlocks the saved login; cancelling sends nothing. The rest of that session needs no further prompts, and backgrounding ends it. If the previous session is idle (a vehicle selected, no request or command check running) and its Hyundai token is valid, it stays in memory while backgrounded and is reused after Face ID without a new sign-in; otherwise nCTRL signs in for you, which never shows the sign-in cooldown warning. Without saved status (first use, or after Sign out & forget) the saved-login screen offers **Unlock with Face ID**. **Sign out & forget** deletes the saved account, saved status and selected-vehicle preference. There is no separate Lock app button. Vehicle navigation appears only after an enrolled vehicle is selected or restored. After unlocking, the previous vehicle opens automatically if still enrolled. An expired or denied session can be re-entered by unlocking or signing in manually. Failed refreshes preserve the last known vehicle state.

## Risk disclaimer

Nothing in nCTRL works until the risk disclaimer is accepted. It states that nCTRL is a third-party, completely unsupported app; that it could damage or disable the vehicle; that Hyundai may ban the account or change its API; and that the user accepts every risk and holds no one else liable. To accept, the user types **I Agree** (case and extra spaces ignored), checks the box and taps **Submit**. On phones, Submit then requires Face ID/Touch ID or the device passcode; cancelling records nothing. Desktop builds are development-only and skip the device check.

Acceptance is per Hyundai account. It is stored in `user://preferences.cfg` as the disclaimer version, acceptance time and the same SHA-256 account hash used for the remembered vehicle (never the email). An acceptance made before sign-in is bound to the first account that signs in successfully. A different account is stopped before any Hyundai request and must accept again; its credentials are held in memory only until it accepts or cancels. **Sign out & forget** clears the acceptance, and a new disclaimer version (`Disclaimer.Version` in `Core/Disclaimer.cs`) requires everyone to accept again. **Backgrounding keeps it. Settings → **View disclaimer** shows the text and acceptance date.

The disclaimer text is not legal advice and has not been reviewed by a lawyer.

## Implemented live functions

- US account sign-in and in-session token refresh, using Hyundai's published-by-community JSON protocol.
- Active vehicle enrollment selection and cached status reads.
- Battery, range, door lock, climate, cable, charging, and separate AC/DC limits where reported.
- Explicit **Wake vehicle and refresh**, separate from cached refresh.
- **Flash lights** and **Horn & lights** (Car screen, third row): one request each, matching upstream (`/ac/v2/rcs/rhl/light`, `/ac/v2/rcs/rhl/hnl`, account and VIN only). When Hyundai accepts, the car art's headlights blink for about 4 seconds, and for Horn & lights a red italic "!" appears above the front of the hood. Refused or failed requests show nothing. The car reports no lights or horn state, so completion is confirmed only through Hyundai's tracking ID (service types `LIGHTS_ONLY` / `HORN_AND_LIGHTS`); without one the result stays unverified, and no status reads follow. They count as remote commands for the request limits.
- Lock and unlock; EV climate start/update and stop, with front seat heat/ventilation (Off, Low, Medium, High) and steering-wheel heat; EV charging start and stop; AC/DC charge targets.
- Command acceptance and transaction-status checks. **Accepted is not confirmed**; successful completion does not fabricate a new vehicle status. Refresh the reported state afterward.
- Vehicle Location automatically retrieves the reported position and displays a tappable map, with Update Location for a new request (existing hourly wake limit applies).
- **The map** marks the car with a small car seen from above, turned the way Hyundai reports it faces (the location's `head`), in your paint color. Each model has a top-down picture named after its side picture (`Assets/<side picture>_top.png`, for example `ioniq_pixel_top.png`: front up, transparent, body in the same pale blue as the side art so the paint applies); without one a drawn car is used. **Your phone's position** shows as a blue dot with its accuracy circle (iOS asks "While Using the App" the first time the map opens). Within 8 km the map zooms out just enough to show you both; farther away it stays on the car and an arrow at the edge points to you with the distance ("You · 3.2 mi"). Your position is used on the phone only: never saved or sent to Hyundai, though map pictures of the area around you come from OpenStreetMap.
- **Send to car** (Vehicle location → Send to car): type an address, which Apple's geocoder looks up on the phone, or paste coordinates or a link shared from Apple or Google Maps. A confirm screen shows the place on a small map with its name and address; **Send to car** sends it to the car's navigation with the request Hyundai's own app uses (`POST /ac/v2/rcs/stc/sendPoi`, `to: GIS`, `actionType: SAVE`, one place with its name, address and coordinates as text), with no phone location or device ID. It goes to Hyundai's map service rather than the car, so it neither waits for nor starts nCTRL's 30-second command cooldown (it still counts toward the daily command cap and stops while Hyundai is rate limiting), and is never retried. Hyundai's 200 reply shows a **SENT TO CAR** dialog and an Activity entry (with Hyundai's tracking ID noted when given; completion in the car isn't checked). It needs Bluelink's Guidance features. The demo accepts sends without contacting Hyundai.
- **Get the car ready after sending a place:** on an electric car, the SENT TO CAR dialog offers **Start Warm up** (your saved preset), or **Start Cool down** when it's 75°F or warmer at the car (from the cold-range temperature; unknown counts as cool), with **Not now** and **Disable this**. Starting sends the preset as a normal climate command (limits and checks apply) and shows the Car screen. Disable this, or **Settings → Offer climate after Send to car**, turns the offer off or back on (kept in preferences).
- **Share to nCTRL:** in Apple Maps, Google Maps, Safari or any app, **Share → nCTRL** sends the place to the car from the Share sheet itself, without opening nCTRL ("Sending Central Park to your car…", then "Sent to your car ✓"). The extension runs nCTRL's own C# `Core`, compiled a second time with NativeAOT into `NctrlCore.framework` (`Native/iOS/CoreLib`, C entry points in `Exports.cs`), so the app and the extension share one codebase: `ShareSender` reads the place (Apple Maps' contact card has its coordinates; a Google Maps short link is opened once to read its pin and name, at most 3 redirects, Google addresses only, no cookies or account details), Apple's geocoder looks up an address, and the send uses the saved login and Hyundai's session that the app keeps in the App Group's Keychain group (the token is renewed if needed, so no new sign-in), through the same request limits as the app (their file is in the App Group). One request, never retried. If it can't send (no saved login, Hyundai refused, no connection), it says why, saves the share and tries to open nCTRL, which shows the place on Send to car the next time it opens: it sends automatically only when the Share sheet didn't try. The extension waits at most 5 seconds for each item the other app provides.
- **Activity → Shared:** every share is listed, newest first, including places the Share sheet sent itself (also added to Requests as "from the Share sheet"): when, from where (Apple Maps, Google Maps or the site), what kinds of items came, and the place or why it couldn't be read. The Share extension also leaves a receipt for each share (only the kinds of items, link hosts, and whether it saved the share and opened nCTRL), so a share it couldn't save still shows, and one that didn't open nCTRL is marked. Tapping a place opens it again in Send to car. The last 20 are kept in their own device-only Keychain item (`com.ngarage.nctrl.shared.v1`); **Clear shared places** and Sign out & forget delete them, and the demo keeps its own list.
- **Widget:** small and medium home-screen widgets and two lock-screen ones show the car's last status from nCTRL: battery, range with the cold estimate, locked or unlocked, charging with its finish time, when it was updated, and the car in its paint on your app color. nCTRL writes `status.json` and `car.png` to the App Group whenever the status or appearance changes (and asks the widget to redraw); the widget itself never contacts Hyundai. They hold no location, VIN, email or account details; the numbers and lock state are hidden on the lock screen while the phone is locked; tapping opens nCTRL. **Settings → Appearance → Show status in nCTRL's widgets** turns this off and deletes the files; Sign out & forget deletes them too, and the demo never touches them.
- **Last known location:** nCTRL keeps the car's most recent location, from a location request or from the location Hyundai includes in a status report, whichever is newer. Opening Vehicle location shows it straight away, without Face ID and also from saved status, under an amber "OLD LOCATION · received 2 hours ago" note; a new location is then requested if the limits allow (asking for Face ID first in each foreground session). When the hourly limit or Hyundai rate limiting refuses a request, or it fails, the old location stays on the map with the note, and the limit warning still offers Send anyway. On phones it is kept only in its own device-only Keychain item (not synced, no Face ID gate, tied to the account and vehicle by fingerprint, never the VIN), overwritten by each newer location, deleted by Sign out & forget and cleared on reinstall; desktop builds keep it while the app runs. It is never used to decide an ignored place. Locked doors and active climate use the red N accent.
- **Look around (Surround View):** on Vehicle location, **Look around** asks the car for one composite picture from its cameras, matching upstream (`POST /ac/v2/svm/findMyCarSVM`, then `GET /ac/v2/svm/getSVMDetails`). A warning comes first every time: it wakes the car, uses the 12-volt battery (with its level when below 50%), and the picture may show people and license plates nearby. nCTRL then checks up to seven times, 15 seconds apart, for a picture newer than the one Hyundai already had, and never sends a second capture request. The picture is kept in app memory only and cleared when the app goes to the background; **Save to Photos** (iPhone only) adds it to the photo library with add-only permission. A capture already running (`HT_533`) and other refusals are explained; Surround View may not be available for every vehicle or account.
- Car art on the Car screen, from the last reported state: a pulsing red padlock with a glint when locked, or an open-padlock outline when unlocked; tapping it toggles the lock like the door button. With climate on, the windshield is tinted red at a setpoint of 72°F or above and blue below (Hyundai reports the setpoint, not whether it is heating or cooling). Front seats are tinted red when reported heating and blue when reported ventilating, and the steering wheel is outlined red when reported heated. Off, unknown or unreported states show nothing. Only the padlock animates, and only while the Car screen is visible.
- **Car health and left-open alerts** from the last report: doors unlocked, any door, tailgate, hood or window open, tire pressure low, 12-volt battery below 50%, brake fluid, washer fluid and key fob battery. The Car screen shows "All closed and locked" or a strip with the most important alert ("⚠ Doors unlocked · +4 more"); tapping it opens **Check your car** with every alert and **Lock** next to unlocked doors. Unknown or unreported items never raise an alert. Alerts are also shown from saved status. **Wake vehicle and refresh** asks first when the 12-volt battery is below 50%, since waking uses it.
- **Open panels on the car art:** the car art faces left, so its left (driver's) side is in view. When Hyundai reports them open, the driver-side front and rear doors, side windows and the hood are outlined in amber on the Car screen drawing. Passenger-side doors and the tailgate are not in view and appear in the alerts only. The nearer seat through the windshield is the driver's, with the steering wheel ahead of it. (Earlier builds outlined the passenger-side reports on this side, and had the seats swapped.)
- **Car name and picture** (Settings → Appearance): **Car name** replaces the model name in the header (up to 20 characters; blank goes back to the model name). **Model** opens a picker of 14 pictures: IONIQ 5 N, IONIQ 5, IONIQ 6 N, IONIQ 6, Kona N, Elantra N, Veloster N and Genesis connect through Hyundai USA (the gas models are marked, since the climate and charging controls are built for electric cars); i20 N, i30 N, i30 Fastback N, Kia EV6, EV6 GT and EV9 are pictures only. The first time a car is connected, nCTRL picks the closest picture from Hyundai's model code (best effort; unknown codes keep the IONIQ 5 N). The picture only changes how the car looks; status and controls always come from the enrolled vehicle. Each picture has its own overlay positions for the padlock, tints, lights and open panels; the Veloster N's driver side has one long door, so it has no rear door or window outline. Name and picture are saved per vehicle in preferences and cleared by Sign out & forget.
- **Ignore this location:** next to "Doors unlocked" in Check your car, **Ignore here** saves the car's current reported location under a name ("Home" first) with a 150 m radius. Unlocked doors there are no longer flagged (Check your car notes "ignored at Home", and the Car screen reads "Unlocked · ignored at Home", never "locked"); open doors, windows and every other alert still show. It needs a fresh car location: one in the same status report, or a Vehicle location request made within ten minutes; otherwise the button is disabled and, when deciding, an unknown or old location never hides the alert. Places are listed and deleted under **Settings → Ignored places**. On phones they are stored only in a separate device-only Keychain item (not synced, no Face ID gate, deleted by Sign out & forget, cleared on reinstall); desktop builds keep them for the session only. The saved status stores only a yes/no "at an ignored place" flag, never coordinates.
- **Charge presets** on the Energy screen: **Daily 80%** and **Road trip 100%** set both AC and DC targets in one request. While charging, Energy shows the charging power and when Hyundai expects the charge to finish ("Charging at 7.2 kW · full at 6:40 AM"), counted from the report's own time. An estimate that has already passed is hidden.
- **Charging on the Car screen:** the line above the car reads **CHARGING · FINISHING AROUND 6:40 AM** in yellow (Hyundai's estimate, while it is still ahead), **CHARGING** when there's no estimate or it has passed, and **NOT CHARGING** in the regular gray; gas cars, which report no charging, keep "YOUR HYUNDAI · LAST REPORTED". Whenever the car reports charging, a yellow line traces just outside the car's shape with a light sweeping clockwise around it, and a yellow light runs counter-clockwise along the edge of the picture's frame. The car's shape is found in each picture once (`Core/Silhouette.cs`: everything between the outermost car pixels of each row and column, so dark grilles and the ground shadow don't break it) and drawn by `Assets/ChargeOutline.gdshader`. If the car is still reported charging after Hyundai's finish time, that report is out of date, so nCTRL reads status once for that estimate, like tapping **Update**. It checks on launch, on returning to the app and every 30 seconds on the Car screen. From saved status this asks for Face ID straight away; cancelling isn't asked again for the same report. It never goes past a limit, runs at most once every 10 minutes, and counts like any read.
- **Moving:** when the status reports a speed above zero, a white dash slides along the bottom edge of the picture's frame, the way the car faces. Hyundai's status is a report, not a live feed, so this shows only when a report was taken while the car was moving.
- **The Climate page** starts with **CLIMATE ON · 76°F**, **CLIMATE OFF** or unknown, from the last report. While the car reports climate on (however it was started), the temperature, seats, steering wheel and front defrost show the car's reported settings, refreshed by each new report; when it reports off, your own choices for the next start come back. Changing a control makes it your choice, and only your own choices are kept in preferences. Front defrost is now read from the status (`defrost`) and kept with the saved status.
- **Climate presets:** **Warm up** (76°F, both front seats heat high, steering wheel, front defrost) and **Cool down** (66°F, both seats ventilate high) start climate in one tap. **Save as Warm up / Cool down** stores the current temperature, seats, wheel and defrost (kept in preferences). A **Front defrost** toggle sits next to the steering wheel; rear-window heat stays off.
- **App color** (Settings → Appearance → App color): one picked color sets the whole look. The default, Performance Blue, is a family of blues all within a few degrees of the accent's hue, so a theme keeps each color's offset from the accent and its brightness, scales its saturation by how vivid the pick is (up to 1.5×; a gray pick gives neutral Graphite), and turns everything to the picked hue (`Core/AppTheme.cs`, `UI/Skin.cs`). Light colors (text, the accent) are never more vivid than the default and give up some color where a hue is too dark to keep 7:1 contrast with the background. The car pictures' backdrops are turned the same way in `Assets/Paint.gdshader`, outside each car's shape. Eight presets (Performance Blue, Teal, Green, Purple, Magenta, Orange, Red, Graphite), a custom color and **Reset to default**. Red (locked, alerts, the N accents), yellow (charging), amber (warnings, open panels) and the heat/cool tints keep their meaning in every theme. The launch screen and app icon stay blue. Saved in preferences; the demo puts it back when it ends.
- **Range & units** (Settings → Range & units): **Imperial** (mi, °F, psi) or **Metric** (km, °C, kPa) for range, climate temperatures and presets, tire pressures, the Details list and ignored-place radius. It changes the display only: Hyundai USA always receives and reports miles, °F and psi, so in metric the climate still steps through the car's 62–82°F, shown to the nearest half degree Celsius (16.5–28°C).
- **Cold-weather range:** Hyundai USA's status has no outside temperature, so nCTRL asks Open-Meteo (`api.open-meteo.com`, no account or key) for the current temperature at the car's last known location, rounded to 0.1° (about 11 km). Below the start temperature, a snowflake and an estimate appear under the range ("~129 mi at 28°F"): the reported range falls evenly to the set loss at the coldest temperature and stays there below it. The defaults are 70°F, 0°F and 50%; all three can be changed in Range & units (5°F or 2°C steps, loss in 5% steps up to 90%), and the estimate can be turned off, which stops all weather requests. It checks after launch, after each Hyundai request and on returning to the app, at most once every 30 minutes for the same area (10 minutes after a failure), with no retries; it uses a separate HTTP client with no Hyundai headers or account data, and keeps the temperature in memory only. With no known car location there is no estimate. The demo uses a pretend 28°F and requests no weather. It is a guide, not the car's own estimate.
- A **Details** tab: tire pressures in PSI (or kPa) with per-tire warning lights when Hyundai reports them, then a scrollable list of every field in the latest status, with readable names for known ones (doors, tailgate, hood, windows, 12-volt and main battery, charging, charge times, climate, seats, steering wheel, warnings, odometer) and the raw field name for the rest. Vehicle location, coordinates and identifiers are never listed. It is filled by the latest read in the current session and kept in memory only; tap **Update** to load it.
- Optional device-bound saved credentials and biometric unlock, masked password/PIN inputs, background locking, sanitized errors, and no automatic command retries.

Missing status fields display **—** or **Unknown**. Server timestamps are shown as supplied; compact timestamps are not assigned an invented timezone. The dashboard is the last reported state, not continuous telemetry.

The shared target endpoint sends both AC and DC targets. Tap **Set AC and DC targets** to send both displayed selections. EV climate requests keep rear-window heat off; front defrost is sent only when chosen. Seat and steering-wheel choices are remembered and sent with each climate start or update in the same single request. The steering wheel uses `heating1 = 3` ("steering wheel only" in the upstream value list) and is sent for any electric vehicle. Front-seat codes (heat 6–8, cool 3–5) go only to generation 3 vehicles, as upstream does; on other generations the seat controls are disabled and a seat request is refused before anything is sent. Rear seats always stay off. Generation 3 requests a five-minute duration. The Climate screen shows reported seat and steering-wheel state when Hyundai includes it. The exact heating values have not yet been confirmed against Hyundai's US servers on a real vehicle. The adapter does not start an ICE engine.

## Account compatibility and limitations

This is an **unofficial US Hyundai-only adapter**, adapted from the current Hyundai-Kia-Connect implementation. It is not an official SDK, and does not support Kia, Canadian, European or other regional accounts.

The source US adapter currently implements username/password token login, not an MFA/OTP challenge exchange. If Hyundai requires MFA, CAPTCHA, a safety acknowledgement or another challenge, this build stops with a sanitized error. It does not bypass checks or automatically retry sign-in. Completing a challenge in the official app is not guaranteed to make this adapter work.

The application uses standard HTTPS validation and does not weaken TLS settings. Hyundai's service can deny an unofficial client or change its protocol. Authentication and commands require a working account and the appropriate enabled services; server acceptance remains authoritative. No claim is made for phone keys, remote performance settings or full Tesla-app parity.

## Sign-in diagnostics

Sign-in failures identify **Authentication** (token request) or **Vehicle list** (enrollment request). HTTP status and JSON API error codes are separate: `HTTP 502` and `HTTP 200; API code 502` are different observations. Neither alone establishes a bad password, outage or endpoint change. Only sanitized stage/status/code text is displayed; raw responses and account URLs are never included. To diagnose a failure, share only that in-app error text, never credentials or network dumps.

## Rename and saved-data compatibility

The display name, visible branding, native biometric prompts and editor plugin label are **nCTRL**. `NGarage.Core`, `IoniqN.csproj`/assembly/solution, `NGarageVault`, native entry points/package names, iOS Keychain service/install marker, Android key prefix/ciphertext filename/AES-GCM associated data remain unchanged. In particular, the literal `N Garage / Bluelink credentials / v1` is cryptographic associated data, not visible branding; renaming it would break existing ciphertext authentication.

Desktop `user://` explicitly stays at `Godot/app_userdata/N Garage` under the OS app-data directory, preserving this checkout's paint and garage preferences. Godot's custom-directory setting only affects desktop; mobile storage remains within the existing app sandbox ([Godot data-path documentation](https://docs.godotengine.org/en/stable/tutorials/io/data_paths.html)). Ecotonic Gray and the existing Cyber Gray preference migration are retained. An older build that stored preferences under `IoniqN` needs a one-time copy of **only** `preferences.cfg` into the retained N Garage directory while the app is closed; no credential files should be copied or converted.

`export_presets.cfg` is intentionally not committed: this is a public repository and presets contain the Apple team ID and bundle ID. Create your own preset in **Project → Export**. New export display names default to the project name, nCTRL. In existing external presets, set Android **Package → Name** and iOS **Application → Name** to nCTRL (or leave blank to inherit). Keep the previously shipped Android package ID/signing key and iOS bundle ID/team/Keychain access group to retain access to saved credentials. If an identity must change, users must sign in and save credentials again; this revision does not migrate secrets between app identities. Freshly export iOS to include its NativeAOT-linked vault and Face ID permission text; see SECURE_LOGIN.md.

### iOS preset for TestFlight

The release flow is: export from Godot, add the widget and Share extension to the exported project, open it in Xcode, then **Product → Archive** and upload to TestFlight:

```
ruby Native/iOS/add-extensions.rb <folder that holds nCTRL.xcodeproj>
```

Godot regenerates the Xcode project on every export, so the script runs after each one. It also builds `Native/iOS/CoreLib` with the .NET SDK (`dotnet publish`, NativeAOT for `ios-arm64`, the same runtime packs Godot's export uses) into `NctrlCore.framework`, packages it with its debug symbols as `NctrlCore.xcframework` (so the archive's dSYMs include it and App Store Connect can symbolicate crashes), embeds it in the app and links it into the Share extension. It needs the [xcodeproj](https://github.com/CocoaPods/Xcodeproj) gem (`gem install --user-install xcodeproj -v 1.27.0`; on macOS's built-in Ruby 2.6, install its dependencies first: `CFPropertyList -v 3.0.6`, `colored2 -v 3.1.2`, `atomos -v 0.1.3`, `nanaimo -v 0.4.0`, `claide`, `rexml`, each with `--ignore-dependencies`). It copies `Native/iOS/Extensions` into the export, adds the `nCTRLWidget` and `nCTRLShare` targets (bundle IDs: the app's plus `.widget` and `.share`, same version and team), embeds them, and puts the app and both extensions in the App Group `group.<app bundle ID>`. The first time in Xcode, select your team on the two new targets under Signing & Capabilities if Xcode asks, and let automatic signing register the new IDs and App Group. `Native/iOS/Extensions/Preview/RenderWidget.swift` draws the widget's layouts on a Mac from a `status.json` and `car.png`. The app's side of the widget refresh is Swift (WidgetKit), compiled into the native vault library by `Native/iOS/build-aot.sh`.

Recommended iOS preset settings:

- **Export Path:** `exports/ios/nCTRL.ipa`. `exports/` is git-ignored except its `.gdignore`, which stops Godot importing the generated project's images.
- **Application → Export Method Release:** App Store. **Code Sign Identity (Debug and Release):** Apple Development, with provisioning profiles left blank so Xcode signs automatically; Xcode re-signs for distribution when uploading.
- **Application → Targeted Device Family:** iPhone. The UI is a fixed portrait phone layout.
- **Numbering:** every TestFlight upload gets a new version (0.7, 0.8, …) with build 1. Set the version in `project.godot` (**Project Settings → Application → Config → Version**, exported as `MARKETING_VERSION`) and leave the preset's **Application → Short Version** blank so it inherits it. Keep the preset's **Application → Version** (the build, exported as `CURRENT_PROJECT_VERSION`) at `1`. Change numbers in Godot, not Xcode: Godot regenerates the Xcode project on every export. Leave **Manage Version and Build Number** on when distributing from Xcode; it only raises the build if App Store Connect already has it.
- **Privacy → User Defaults Access Reasons:** CA92.1 (“Access info from same app”). The iOS vault stores its install marker in `NSUserDefaults`.
- **Plugins:** leave any legacy NGarageVault `.gdip` disabled. The enabled **nCTRL Secure Vault** editor addon adds `NSFaceIDUsageDescription`, `NSPhotoLibraryAddUsageDescription` (add-only, for saving Surround View pictures) and `NSLocationWhenInUseUsageDescription` (your position on the car map) to Info.plist; without it the app cannot use Face ID and stays locked at the disclaimer. Godot's iOS template already sets `ITSAppUsesNonExemptEncryption = false` (the app uses only standard HTTPS); the addon must not repeat template keys. After exporting, confirm `NSFaceIDUsageDescription` and `NSPhotoLibraryAddUsageDescription` are present in the generated `nCTRL/nCTRL-Info.plist`.

## Storage, request limits and errors

With saving enabled on a supported phone, email/password/PIN are kept in the Apple Keychain (encrypted by iOS, readable only while the phone is unlocked, never synced) or Android Keystore-backed encryption. Tokens, enrollment, live location requests and history remain memory-only; only the last known car location is kept, in the device Keychain (see above). The last vehicle status (battery, range, doors, climate, charging, targets, seats, reported and updated times), vehicle name, last six VIN characters and generation are saved in `user://vehicle-snapshot.json` so the app can open to it; it holds no location, email, full VIN or credentials, identifies the account and vehicle only by SHA-256 hashes,. Sign out & forget deletes it. A session kept while backgrounded, and the saved login read for the current foreground session, stay in app memory only. Public map tiles are cached under `user://map-cache` for at least seven days; they can reveal the viewed area, but contain no vehicle marker, account data or credentials. Locking drops session references; this is not guaranteed zeroization of managed strings. Paint, garage name, each car's name and picture, and an account-scoped SHA-256 vehicle fingerprint go into `user://preferences.cfg`; car names and pictures are stored under that fingerprint, never the VIN. The fingerprint is only a selection preference, contains no raw email/VIN/credentials, and is checked against current authenticated enrollment. Sign out & forget clears it. See `SECURE_LOGIN.md` for platform setup, exact protection and device-test limitations.

The adapter serializes operations. Hyundai publishes no US request quotas, so nCTRL enforces its own conservative limits (`Core/RequestBudget.cs`):

| Request | Cooldown | Daily cap |
|---|---|---|
| Sign-in (token request) | 60 seconds | 20 |
| Cached status read | 15 seconds | 150 |
| Wake vehicle and refresh | 10 minutes | 10 |
| Remote command | 30 seconds | 30 |
| Location | 1 hour | 24 |
| Surround View capture | 5 minutes | 6 |

The limits are shared by every account and client on the device and saved in `user://request-limits.json` (counts and timestamps only, no account data). Locking, relaunching, signing in again and Sign out & forget do not reset them. Daily caps reset at local midnight. The vehicle read when a session starts counts toward the daily cap and starts the read cooldown but is never refused by it. Command tracking checks and Surround View picture checks count toward the read cap without a cooldown. Automatic token renewals (about once a day) are not budgeted. Settings → **Request limits** shows what is left.

When a limit refuses a request you tapped, a warning explains it and offers **Cancel** (nothing is sent) or **Send anyway**. On phones, Send anyway requires Face ID/Touch ID or the device passcode. An override covers that single request, still counts, and is recorded in Activity. Every later refusal warns again. Automatic requests never prompt; they skip whatever the limits refuse.

When Hyundai answers HTTP 429, every request pauses for the server's Retry-After (or five minutes, capped at 24 hours), with no override. That request type's limits then tighten for 24 hours: the cooldown doubles and the daily cap halves, stacking up to ×8 on repeated 429s, and return to normal after 24 hours without one.

After submission, the UI automatically makes up to eight follow-up checks, 15 seconds apart (network time is additional), and disables further commands during those checks. Backgrounding/sign-out cancels the monitor. Successful early confirmation retains the command cooldown.

HTTP 200/empty-body commands are treated as accepted. The receipt displays HTTP acceptance; automatic GETs then check transaction status and cached vehicle state. **Check last command has been removed.** A control shows … while checking, ✓ after confirmed completion or a matching changed vehicle report, ! for reported failure, or ? if unverified. A tracking SUCCESS is completion evidence, but button colors still follow reported vehicle state, never an optimistic local toggle. Without tracking, a changed report timestamp and a transition to the requested state are required; unchanged/already-matching reports do not establish completion. Failed reads preserve last known state. Automatic checks never wake the vehicle or repeat a command POST. Rate limiting/access denial ends monitoring; unresolved outcomes remain explicitly unverified.

Climate On sends exactly one POST to /ac/v2/evc/fatc/start, with no charging request or charging fields. Charging POSTs exist only behind the explicit Start/Stop Charging controls. The offline regression suite checks this request count and payload isolation. It cannot determine why the owner's vehicle began charging or establish what an older phone build sent.

The map uses only visible HTTPS OpenStreetMap tiles, a separate account-free HTTP client, `nCTRL` identification, visible attribution, seven-day caching and conditional revalidation, following [OSM tile policy](https://operations.osmfoundation.org/policies/tiles/). Viewing shares the map area with OSM; tapping the map shares the exact vehicle point with the external maps app. Android uses a package-free geo: intent; iOS tries the system geo-navigation:///place?coordinate= URL and falls back to Apple Maps if dispatch fails. [Apple documents default navigation](https://developer.apple.com/documentation/MapKit/preparing-your-app-to-be-the-default-navigation-app) as region/OS dependent. Returning from Maps still locks the session as required. Reopening location within the hourly cooldown shows the last known location, marked old, without a request; after cooldown it requests a new point. Refused or failed location requests keep the last known location on the map, marked old. No device GPS permission or backend is needed.

The owner reported “Request accepted; no tracking ID. Refresh status to verify” after a command. That code path requires a successful HTTP response without a detected API error; it establishes submission and a Hyundai server response, not physical vehicle action. The original routes/payloads followed the upstream US implementation. A subsequent direct comparison with fiveN found its extra door-body PIN and minimal command headers; nCTRL now matches those, and applies the common header profile to every command. See [FIVEN_COMMAND_COMPARISON.md](FIVEN_COMMAND_COMPARISON.md) for measured request equivalence and intentionally retained differences. No evidence currently establishes why the vehicle did not respond. Without a tracking ID, automatic checks use reported vehicle status; cached reads can lag. No command replay, endpoint changes or fabricated completion were introduced.

Location is requested when its screen opens or Update Location is tapped. Command follow-up runs only while the session is unlocked. There is no background polling, telemetry, backend or cloud credential storage.
